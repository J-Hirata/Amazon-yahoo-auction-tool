## 保存処理

- 既存の `read` / `update(callback)` を維持する。既存画面や紐付けID・後継履歴・メモ・画像・通知履歴を一括で別形式へ作り直さない。
- 第一移行は `link-monitor` と `draft-items` のJSONBドキュメント。行ロックと同一接続のトランザクションで更新し、複数プロセスによる読み直し/保存の競合を防ぐ。変更版番号による古い更新の拒否も用意した。
- このJSONBは既存機能の移行のための保存形式。場所別在庫の残高/取引/移動台帳や注文履歴はまだ実装していない。後段で商品/場所/取引を正規化し、同じ数量を二つの台帳で更新しない設計へ進める。
- 2026-10-26に販売判断用の最小注文履歴 `salesTracking` を同じ文書へ追加した。上の注文履歴未実装は保存層初回の状態。追跡開始時刻/対象SKU/注文ID+明細ID/数量/状態/差分イベント/確認済み期間/排他を保存し、FBAや現物残高を二重減算しない。場所別残高/移動台帳はまだ未実装で、追加DDLや別DBは作っていない。本番15組/14 SKUの開始・初回の空応答保存を確認済み。
- JSON側も原子的な一時ファイル保存と同一ストア内の直列更新に統一。下書きのAPI保存は、取得済み一覧全体の上書きから最新状態への更新へ変更した。JSONの複数プロセス共有までは保証しない。
- DB接続/SQLに失敗しても空のJSONへフォールバックしない。未初期化のDBは明示エラー。COMMIT応答が失われたときは保存結果不明として、無条件の再実行をしない。
- 既存通知の送信待ちは保存処理と同じドキュメント内に残るが、DB化だけでマルチプロセスの自動通知が完成したとはしない。旧DB試行のGmail処理/自動実行は引き続き無効。クラウド版だけ別の限定APIでSMTP接続確認と全体1回の手動テストを提供し、送信前のDB確保・重複防止・受付後の保存不明時の再送禁止を実装した。定期ジョブ/注文履歴/現物残高は未実装。

## 接続情報

DBを選ぶには `ASIN_STORAGE_BACKEND=postgres`、このツール専用の `ASIN_DATABASE_URL` と `ASIN_DATABASE_EXPECTED_HOST` が必要。他ツールの汎用 `DATABASE_URL` を勝手に使用しない。接続先一致とTLS証明書検証を必須とする。

開発用の接続情報はプロジェクト直下の `.env.neon-dev` へ保存済み。現在のWindowsユーザーとSYSTEMだけのACLにし、Gitの除外も確認した。内容は表示・コミット・共有しない。通常の `npm start` はこのファイルを自動読込しない。クラウド公開時は開発用所有者資格情報をそのまま使わず、最小権限と公開先の秘密設定を別に用意する。

DBモードの現サーバーはループバック限定。同一Origin/許可Host以外を拒否する。これは検証用の境界であり、本人認証の代替ではない。旧JSONモードのAPI全体をクラウド公開してよいという意味でもない。


実データの移行コマンドには別途 `--apply` と `--confirm-host` が必要で、現時点のコマンドは明示したdevelopment環境以外を拒否する。今回これを15組/58件へ適用していない。元のJSONは保持し、現在版で稼働し続ける。

2. 公開用アカウント/秘密設定/権限、DBへの最小アクセス、監査と復元、クラウドでの排他/取得再開位置を実装する。
