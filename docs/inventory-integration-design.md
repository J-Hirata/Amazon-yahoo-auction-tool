### 通知の目的を拡張: Amazonでの売れ行きと併売の継続判断

2026-10-25 第3問への本人回答を反映。ヤフオクは余剰/滞留在庫を売る販路として使い、Amazonでしっかり売れることが分かればヤフオクの併売を止める予定。判定基準や停止は本人判断であり、自動停止条件を決めたわけではない。

- 50個から49個、3個から2個のように、在庫が正のままでもAmazonで1個売れたことを知らせたい。少数・大量のどちらも対象とし、「0個になるまで通知しない」設計にはしない。
- ヤフオク終了時には、自社Amazonの現在庫と「紐付け開始から何個売れたか」を一緒に確認したい。売れ行きと在庫を見て、再出品・価格見直し・併売停止・保留を本人が判断する。
- 「終了した商品の再出品判断」だけを最初の目的に絞った直前案は不足していた。既に併売中の商品でAmazonが売れ始めたことの通知も、第1段階の追加要件に含める。

| 通知/表示 | 根拠と内容 | 誤認を防ぐ条件 |
| --- | --- | --- |
| Amazonの販売/受注 | 自社の対象SKU・状態の注文/販売記録に基づき、今回の数量、紐付け後累計、現在庫/確認時刻、ヤフオクの状態/リンクを表示 | 在庫差分だけで「Amazonで売れた」としない。未確定注文・出荷済み・取消・返品を分ける |
| FBA数量の減少 | 同じ対象/範囲で有効な観測を比較し、前回/現在数量と時刻を表示。理由未確認ならそのまま通知 | 予約・移動・使用不可・返送・他販路MCF等をAmazon販売に置き換えない。欠損/古い値/範囲変更は比較不能 |
| ヤフオク出品終了 | 自社FBA数量と鮮度、紐付け後のAmazon販売/受注累計、再出品先の確認状況を併記 | 終了理由・後継出品不明は要確認。自動再出品の途中か最終終了かの通知方針は未確定 |
| 併売方針の見直し | 追跡期間・売れ行きの根拠を見せ、継続/ヤフオク停止検討/価格見直し/保留と次回確認を本人が記録 | 1個売れただけで自動的にヤフオクを止めたり、両販路を値下げしたりしない |

最小の文面例は架空データとして「Amazonで1個の注文を確認しました。自社FBA取得分は49個。追跡開始後の注文確定数は1個です。ヤフオク併売を続けるか確認してください。」とする。未出荷/出荷済みは実際の根拠に合わせて明示し、確認できない場合は「販売数不明」とする。実際の1件を確認した通知ではない。

### 販売履歴と数量履歴を別に保持する

1. Amazonで購入された注文と、ヤフオク/楽天等へ送るMCF出荷を区別する。MCFでFBAが1個減ってもAmazon販売1個にはしない。元の販売先が分からない記録は分類保留とする。
2. 販売の根拠候補はAmazon Orders API/販売レポート、既存の注文データ、プライスターの注文CSV。接続権限・期間・取得列・遅延・分類を承認後に限定検証する。現在庫CSVだけでは足りない。CSV手動取込は履歴の補完には使えるが、自動取込と同等の継続通知ができるとは約束しない。
3. FBA在庫APIは引き続き登録対象限定。注文の取得がSKU直接指定に対応するかは接続方法ごとに確認する。絞れない場合も国/更新期間/件数に上限を設け、対象SKU以外を保存しない方式を検討する。全注文/個人情報を無条件に取り込む設計にしない。
4. 集計は販売先・アカウント・国・SKU・状態・期間で行う。同ASINの別SKUを合算せず、同じSKUにヤフオク2出品があってもAmazon注文を二重に足さない。
5. 主表示は集計定義を付けた「紐付け後のAmazon注文確定数(キャンセル除外)」を候補とし、出荷済み数/取消数/返品数は別項目にする。未確定は未確定。本人の第5問回答により、注文確定を確認した時点で未出荷でも次の1時間通知の対象にする。出荷後に同じ1個を再度販売通知しない。取消/返品は訂正履歴を残し、返金だけで現物在庫を戻さない。
6. 在庫は増減を時系列で記録するが、開始50個・現在49個から累計販売1個を計算しない。1個売れて1個補充されて残数不変でも、販売記録があれば販売通知の対象にする。数の差と売上が一致しない部分は理由不明のまま残す。
7. 注文/行IDと取得元の業務キーで履歴を更新し、同じ注文のAPI再取得・重複CSV・クロスマ経由の複製で累計や通知を増やさない。取得完了位置と通知済みイベントを保存し、取得途中の失敗で履歴を完全取得済み/販売ゼロにしない。
8. この履歴は売れ行きの判断材料であり、取得済みFBA残数から売上個数をもう一度減らすためには使わない。手元在庫の注文反映とは担当を分ける。

### 紐付け開始の扱い

- 初回紐付け日、履歴を取得できた開始日、通知を有効にした時刻、開始時の数量スナップショットを別項目とする。再確認日時の `reviewedAt` は現コードで更新されるため、そのまま不変の販売集計起点に流用しない。
- 同じ現物/SKUの追跡を継続する後継出品への引継ぎでは、累計開始日を勝手にリセットしない。解除後の再登録や商品/状態変更は、同じ追跡を継続するか新しい期間にするかを本人確認する。
- 既存15組について過去の初回日/販売記録が確認できれば補完できる候補。今ある在庫スナップショットだけでは、10月21日からの販売数を復元できない。不足時は「確認できた期間の累計」「開始日/過去分未確認」と表示し、紐付け以来の全期間と偽らない。
- 過去履歴の初回取込は一覧補完に使い、過去の注文を全て新規メールとして送らない。通知対象の開始時刻と履歴対象期間を分ける。
- 現行ローカル版のPC停止中、または将来のクラウド処理障害中に欠けた履歴は、取得元で許される期間と上限内で再取得・重複排除する案。取り切れない期間は欠落区間を表示し、売上ゼロとしない。

この追加要件は後段の「販売可能日からのAmazon販売テスト」と共通の販売履歴を使う。ただし、今回の紐付け後の経過観察と、販売可能日起点のテスト期間は別であり、起点を混同しない。販売テスト全体の完成まで、併売中商品の販売通知を先送りしない。

### 第4問回答: 1時間確認・売れたときだけ販売通知

2026-10-25 本人回答で、追加機能の販売確認は1時間ごと(60分)に変更する。毎正時固定という指定ではない。前回の30分案より、この回答を優先する。今回コード/設定は変更しておらず、現在版の初期値・再予約処理・画面文言は30分のまま。

- 新しく確認できた販売がある場合だけ、その回の商品と数量を1通にまとめる。1個の販売も省略しない。売れていなければ販売通知を送らない。次の確認で同じ注文をまた知らせない。
- 取得できなかった場合を「販売0なので送信不要」と扱わない。集計範囲や欠落を記録し、必要な確認不能の案内は販売通知とは区別する。
- 「売れていなければ送らない」は販売通知の空報告をしない方針。従来の在庫0・出品終了・取得失敗等の要対応通知を一括で無効にする意味とは解釈しない。それらの送信タイミング/まとめ方は別に確認する。
- 現行ローカル版はPC/サーバー停止中は動かない。第7問のPC常時起動不可という回答を受け、追加設計ではクラウド側で確認・通知する構成を提案する。処理障害からの再開時は新しい販売を重複排除してまとめ、欠落時間分の空メールや同じ注文のメールを連続送信しない。
- 60分対応は設定欄だけでなく、成功/失敗後と設定保存時の次回予定、初回予定、画面文言、試験を一緒に変更する必要がある。30分固定の現コードで1時間対応済みと表示しない。実装/有効化は別工程。

### 第5問回答: 注文確定時に販売通知へ載せる

2026-10-25 本人は「注文確定時に知らせてほしい」と回答。出荷確定を待たず、注文の確定を取得元で確認できた時点から、次の1時間通知の対象とする。注文の発生時刻・確定を確認した時刻・メール通知時刻は別に記録し、即時到着を保証しない。

- 未確定/保留中の注文を確定と推定しない。利用するAPI/CSVの状態と注文確定の対応は、接続前のサンプル検証で確認する。
- 本文は注文確定を伝え、未出荷ならその旨を表示する。出荷後は履歴の状態だけを更新し、同じ注文をもう一度新規販売として計上/通知しない。
- キャンセルは元の記録に対応付け、取消除外の累計を訂正し、取消前後の履歴を残す。既に送ったメールの内容が取り消されたことを画面で確認できるようにする。取消だけが起きた回の訂正メールの扱いは、空の販売報告とは別に今後確認する。
- 返品/返金とキャンセルを一括で扱わない。現物の戻りは受領/検品のルールに従い、通知や累計の訂正でFBAの観測残数を再加減算しない。

### 売れ行きに応じた併売終了

本人意向: Amazonである程度回ると判断した商品は、ヤフオク販売を止めて連携を解除する場合がある。「ある程度」の数量/期間は固定していない。本人判断を記録し、自動停止や閾値による強制解除にはしない。

提案する手順は「Amazonの売れ行き確認 -> 本人が併売終了を選ぶ -> 対象ヤフオク出品を本人が停止/終了 -> 停止確認 -> 当該併売の監視を終了し履歴を保存」。停止が未確認なら「併売終了の手続き中」とし、解除だけで販売が止まったと見せない。外部出品停止の実行主体は当面本人とする。

現コードのDELETEはローカルのlinkを配列から外してログを残すだけで、ヤフオクの停止処理は呼ばない。link内の後継ID履歴も永続的なアーカイブへ移す実装ではない。そのため「解除後も履歴を保存する併売終了」は未実装であり、現機能がそのまま対応済みとは扱わない。

追加案では、追跡ID/初回日、Amazonの注文/数量履歴、対象ヤフオクIDと後継履歴、終了日時・理由・停止確認の根拠を残す。監視の終了と履歴の削除は別操作。意図的に止めた出品を出品漏れ/再出品候補として毎回通知しない。併売を再開する場合は過去期間を残し、新しい期間との関係を明示する。

同じSKUに複数ヤフオク出品がある場合、終了する対象IDを確認し、他の出品まで解除/停止したことにしない。解除後もAmazon単独で追跡を続けるかは別の選択とし、勝手に監視/通知を継続する仕様にはしない。

### 第6問回答: 現物在庫は手入力、PCとスマホの両方で操作

コンテナ・自宅/自社の在庫は、本人による登録・数量増減・棚卸し・移動から始める。販売分の自動減算を初回の必須機能にしない。スマホ回線で現場入力でき、PCでも検索・一覧確認・連続入力がしやすい画面とする。

### 追加要望: 少数のカタログ作成待ち

| プライスター現在庫 | 公式はSKU、ASIN、number、price、cost、Condition、conditionNote等を説明 | 現在庫CSVだけで最終販売日を得られると約束しない。numberは出品数量であり自宅の棚卸し実数ではない |
| クロスマ中古/楽天 | 公式は中古商品取得、ASIN個別入力、写真登録等を案内 | 本人認識の5〜6件貼付の実画面と件数上限は未確認。機能一般と自社設定の有効化を分ける |
| クロスマの在庫連動 | 併売/専売の設定で挙動が異なり、専売の固定在庫からの減算もある | 中古なら全て自動連動、新品なら全て楽天出品済み、とは推定しない。実商品1例で担当とIDを確認する |
| コンテナ/自宅の実数・状態 | 本人による登録・棚卸し・写真・メモ | 写真から個数を自動確定しない。未確認の基準数を現在庫へ入れない |

API候補は利用許可・現アカウントの権限を保証しない。まず必要な項目だけのサンプル/CSVで検証する。注文の個人情報を初期の判断一覧へ保存しない。追加権限・料金・認証操作は事前説明し、秘密値をチャットへ貼らせない。新品の楽天出品は既存クロスマ運用を尊重し、Amazonのテスト終了を一律の出品条件にしない。

## 4. 商品・在庫・販路を分けるデータ設計案

以下は論理設計であり、DB製品やスキーマ確定ではない。

| 概念 | 識別・保持する情報 | 混同しないもの |
| --- | --- | --- |
| 管理商品 | ツール内管理ID、名前、写真/出所、単位、状態、付属品/セット、メモ。ASINなしも可 | ASINは共通カタログ番号。状態違い/色違い/付属品違いを勝手に同一現物群へ統合しない |
| Amazon SKU対応 | アカウント+国+Seller SKU、ASIN、FNSKU、状態、確認根拠。必要時は対応の有効期間 | 別SKUが同じ現物群を指す場合も、本人確認なしに統合しない |
| 保管場所 | コンテナ、自宅/自社、FBA。必要なら棚番号 | 販売先や配送方法ではない。単なる場所移動で出品を増やさない |
| 現物残高・移動 | 商品ID+場所、状態別残高、取引履歴、棚卸し時刻、変更版番号 | 出品数は現物の追加ではない。FBA観測は手入力の増減とは別 |
| 販路出品 | 販売先/アカウント/出品ID、URL、発送方法、出荷元在庫群、必要な単位数、観測 | Amazon FBA販売・Amazon自己発送・ヤフオクMCF/自社発送を別条件にする |
| 出品予定 | 出す予定/様子見/意図的に出さない/方針未設定、理由、次回確認日 | 予定していない販路を未出品異常にしない。方針未設定は要設定であり出品漏れ確定ではない |
| カタログ準備作業 | 管理商品ID、カタログ作成待ち/作業中/登録確認、メモ、任意の見直し日、後から付けるASIN/SKU | 作業状態は保管場所/数量ではない。ASIN追加を追加入庫や購入可能状態にしない |
| 注文/引当の参照 | 外部注文・行のID、担当、状態、実在庫への反映/未反映、正規化先 | クロスマ経由とAmazon/CSV経由の同じ注文を別売上にしない |
| 観測 | 取得元、sourceObservedAt/取得時刻、対象範囲、完全性、品質、失敗、元データの参照 | 不明/古い情報/未照合/取得失敗をゼロへ変換しない |
| 販売テスト/判断 | SKUまたは状態を特定した商品、販売可能日/根拠、期間、売上範囲、方針、理由、再確認日 | 登録日・納品発送日・出品作成日とは別 |
| 追跡期間/販売事実 | 初回紐付け/追跡ID、履歴の取得範囲、販売先/アカウント/SKU/注文行、数量/状態/訂正、通知開始/通知済み記録 | 在庫差分を販売にしない。再出品で履歴を消さず、同じ注文を複数リンクで二重計上しない |
| 問題/通知/作業 | 問題ID、状態遷移、本人対応、通知送信待ち/結果、楽天作業の段階 | 問題の発生とメール到着、リンクを開いたことと出品完了を分ける |

ASIN入力の手軽さは維持する。通常はSKU手入力を要求せず内部取得する。複数SKUや中古状態がある場合だけ、写真・状態・付属品で本人が選択する。選べない場合はページの紐付けだけを保存し、現物在庫との結合は保留。既存15組は同じASINを理由に一括で統合せず、確認状態を維持して参照を追加する。

### 数量と単位

- 手元の現物は、使用可能・引当済み・使用不可・検品待ちなど相互に重ならない区分で管理する。移動中は出荷元/到着先の棚残高とは別にする。
- 手元の販売可能数は「確認済み使用可能数から未反映の確定引当を除いた値」。その引当が既に残高区分に含まれるなら再度引かない。負数・整合しない内訳は要確認とし、黙って0へ丸めて正常に見せない。
- FBAはAmazon観測を数量の正とし、ローカル売上や受領入力で観測値に足し引きしない。未反映の外部確定引当だけを別記し、FBAへ反映された根拠を確認した時点で二重控除を解除する。経過時間だけで反映済みとしない。
- 一つの在庫群を複数販路で共有する場合、各出品に同じ販売可能数を参照させる。販路別数値を足して総在庫にしない。MCF適格性・配送先依存は別表示。
- 未確認の場所がある場合は「確認済み計○、未確認あり」。FBA totalに含まれる納品中とローカル移動中等の重複を解消できなければ総数を確定表示しない。
- 台/個/箱を商品ごとに保持する。学研15箱を15個へ自動変換しない。箱→個の換算は内容数の確認後だけ。セット組み替えは初回の自動処理対象外。

## 5. 数量操作・注文・移動のルール案

第6問回答により、コンテナ・自宅/自社は初期段階では以下を本人が手入力する。販売時の減少も理由を付けて記録し、FBAへの持ち出しは通常の減少ではなく移動を選ぶ。FBAの観測数量を手入力台帳として書き換える機能ではない。将来の自動注文連動は、手入力済み記録との対応を照合してから追加する。

| 操作 | 振る舞いと保存するもの |
| --- | --- |
| 新規登録 | 名前・場所・数量・単位・状態を最小入力。ASIN/写真/メモは後から可。重複候補は示すが自動統合しない |
| 追加/減少 | 「3個追加」は現在数+3。「減らす」は理由付きの差分。変更前後・場所・理由・操作者・日時・一意な操作IDを一体保存 |
| 棚卸し | 「実数を3個にする」は観測した絶対値。差分と棚卸し時刻を表示して確定。入力開始後に売上/移動があれば古い値で上書きせず再確認 |
| 使用不可 | 売却・廃棄ではなく、使用可能区分から使用不可へ振替。実物総数は減らない。修復後の復帰も履歴付き |
| 場所移動 | 同じ取引で出荷元を減らし、移動中へ計上。到着確認で移動中を減らして到着先へ。部分到着・破損・取消は別の確認記録 |
| 訂正 | 過去履歴を消して書き換えず、訂正/取消の取引を残す。最初は本人ひとりでも更新版番号で二重操作を検出 |

例: コンテナ10台から4台発送 -> コンテナ6台・移動中4台。3台だけFBA受領を確認 -> 移動中1台を継続表示。FBA受領数は納品ID/受領根拠で移動と照合するが、FBAスナップショットへ3台を足さない。FBA残数の純増3だけでその納品の受領完了を推定しない。対応できない受領は照合待ちにする。

### 売上・キャンセル・返品

現実装に注文連動台帳はない。フェーズ2Aは本人の手入力と観測で成立させ、以下の注文自動連動は将来案として区別する。手入力の販売記録と後の注文取込を同じ取引へ対応付け、二重減算を防げない状態で自動化へ切り替えない。

- 本ツールが数量処理を担当する自己発送在庫: 確認できた注文確定で引当、出荷確定で現物を減らして引当解消。注文と出荷で二回減算しない。各販路での確定の定義は接続時に確認する。
- 出荷前のキャンセル: 引当解除だけ。未出荷の現物を増やす入庫にはしない。出荷後のキャンセル/返金: 現物返却を確認するまで在庫を戻さない。
- 返品: 手元で受領 -> 検品待ち -> 使用可能/使用不可。返金だけでは再販可能にしない。FBA返品はAmazonの観測/根拠へ従い、別途同じ戻りを加算しない。
- クロスマ担当/FBA観測担当: 注文イベントは販売判断と照合用に記録し、当ツールから同じ数量を再減算しない。設定不明は「連動未確認」で、自動減算しない。
- 在庫群+イベント種別ごとに処理担当を定義する。クロスマが販路表示を更新しても、自宅の現物記録をどこが更新するかは別途確認する。「クロスマに任せる」と書くだけで現物残高が最新とみなさない。
- ASIN/数量/時刻だけで同一注文を決めない。販路+アカウント+注文ID+行ID+処理種別/版を基本キーにし、クロスマ経由の元注文IDを正規化する。元IDなしのCSVは照合保留にする。
- CSVはまず読取・照合・差分プレビュー。ファイルハッシュに加えて業務キーで重複を判定し、同じ行を別ファイルで再取込しても増減しない。残高スナップショットを入荷・売上の差分として適用しない。

## 6. PC非依存のクラウド構成とPC/スマホ画面

現在のHTMLはスマホ幅に対応しているが、`link-monitor-api.js` の保存操作はループバック元だけ許可する。`server.listen(port)` は外部接続を明示的に制限しておらず、旧APIには広いCORSもある。ログイン・HTTPS・外部用の権限境界もないため、ポート開放やlocalhostをIPへ変更するだけの公開はしない。

### 最小構成案

第7問でPC常時起動不可と確定したため、前案のPC私設接続とローカルSQLite単独を本番案から外す。既存Neonを保存基盤の第一候補とし、同じツールの画面と処理をクラウドへ配置する。新しい別台帳やアプリを増やす意味ではない。

| 役割 | 構成案・確認事項 |
| --- | --- |
| 画面の公開 | 既存HTML/JS/CSSを活かしたVercelのサンプル確認版を実配備済み。通常はPC/スマホから同じURLを開き、PC常時起動/PowerShell起動を不要にする。確認版はブラウザ内保存だけで、業務版の本人認証/Neon共有保存/移行/利用条件・費用の確定は次工程。契約変更は未実施 |
| ログイン/API | 本人のアカウントだけ許可。既存ロジックを認証付きクラウドAPIから呼ぶ。既存のログイン基盤があれば再利用し、なければNeon Auth等を比較。1人利用でも無認証公開しない |
| 永続保存 | 既存アカウントのNeon上のPostgresを第一候補。紐付け・商品・場所・数量履歴・操作ID・観測・通知履歴を保存。ブラウザへDB接続文字列を渡さない |
| 写真/添付 | 私有のオブジェクトストレージを候補とし、DBには参照/出所/権限を保存。スマホやPCのローカルパス、関数の一時ディスクを正本にしない。Neonの対応リージョン/利用可否は別確認 |
| 定期確認 | クラウド側のスケジュールから読取処理を起動。Neon Functions/スケジュールも候補だが、既存リージョン・制限・費用を確認する。ブラウザを開いている間やPCのsetIntervalへ依存しない |
| 実行/送信の耐障害性 | 実行ID・取得完了位置・排他/期限付き実行権・送信待ち/結果を永続保存。重複起動や中断後も二重増減/通知を防ぐ。関数やタイマーだけを永続キューの代わりにしない |
| 外部接続/メール | Amazon等の必要最小の秘密情報はサーバー側の保護された設定へ。メールはクラウド対応のSMTP/API送信方法を別途検証し、送信先/試験/有効化を承認してから使う |

画面/APIのホストと定期処理を同じ実行基盤へまとめるか、Neonの関数を使うかは、既存サービス・稼働制限・外部接続条件から選ぶ。画面の全面的なフレームワーク変更やAI用DB/AI Gatewayは必須にしない。Neon Functions/ストレージには対応リージョンの制限があるため、既存DBを確認せず利用可能と断定したり、勝手に移動したりしない。

本人のNeonはVercel管理の組織で、Neon画面のNew projectが無効だったため、既存VercelのStorage -> Create Storage -> Neonから作成した。専用保存先は第0節の `amazon-yahoo-inventory` を使う方針。その後本人はVercelでの継続を希望し、専用アプリを作成/連携して配備設定と実開発DBでの画面保存を試験した。DB/Vercelプロジェクトの作成をアプリ公開済みとせず、定期処理の構成もまだ確定しない。開発ブランチは試験の隔離であり、別アプリの恒久的なデータ分離と同一視しない。

### 秘密情報とローカル依存の置き換え

- 現Gmail処理はWindows PowerShellとWindowsユーザー専用の暗号化資格情報に依存する。資格情報ファイルをクラウドへコピーして使えるとは扱わず、クラウド用送信経路を別に設計する。今のGoogle認証を開いたり、アプリパスワードを作り直したりはしない。
- Amazonの現設定読込には別プロジェクトのPC上の.env参照がある。そのファイルや秘密値を設計文書へコピーせず、移行承認後に必要項目と権限を絞って安全に設定する。
- HTTPS・本人認証・API権限・Origin/CSRF対策・セッション期限・監査/復元を用意し、端末へ管理用キーを配らない。秘密値をチャットへ貼らせない。公開先の一時ディスクへ業務データを保存しない。
- 既存Chrome拡張/ローカル入力補助は利用時にPCが必要な機能として経路を別に検証する。そこへの依存を、場所別在庫のスマホ入力や監視へ持ち込まない。
- 圏外/クラウド障害/認証切れでは「未保存」を明示。サーバー確定前に保存済み表示をせず、再送は同じ操作IDで行う。PC電源オフ自体は未保存の理由にならない構成にする。

### 画面案

既存ツール内に「商品・在庫」「要対応」「販売の見直し」の入口を順次追加。下書きQは既存の出品作業として残す。初回から全メニュー・全設定を表示しない。

- 商品・在庫: 写真と商品名、場所別数量、要点の販路状態、メモ。検索と場所フィルターを中心にする。SKU・全リンク・根拠・時刻・履歴・補充候補は詳細で確認でき、必要時に列を増やせる。
- PC: 比較しやすい行一覧と検索/絞り込み、キーボードでの連続入力を中心にする。スマホ用の縦積み表示をPCへ強制しない。まとめ操作は対象/差分プレビュー付きとし、1商品ずつの登録だけに限定しない。
- スマホ: 商品を選ぶ -> 場所 -> 「追加」「減らす」「棚卸し」「移動」の操作を分離 -> 確定。棚卸しは大きい数値入力を中心にし、写真とメモを任意追加。1商品を小さい多列へ押し込まない。
- カタログ作成待ち: 同じ一覧の作業状態フィルターで少数の待ち商品を取り出す。商品詳細でメモ/任意の見直し日を編集し、ASIN/SKUは作成後に同じ管理IDへ追加。別台帳・専用の大画面・期限必須にはしない。
- 詳細: 場所別在庫、販路/発送方法、Amazon SKU、ヤフオクIDと後継履歴、写真と自社コメント、取引履歴を分けて表示する。セット違いをここで選べるようにする。
- 要対応: 「何が問題か」「次に何をするか」を先頭にする。商品名/写真、場所、確認済み数量、出品リンクを続け、技術項目は折りたたむ。件数は商品数と問題数を区別する。
- 販売の見直し: 様子見の期限、滞留候補、本人の判断と次回確認、クロスマでの作業段階を表示。管理番号やASINだけの一覧にしない。
- 常設の全行保存ボタンを並べず、メモは編集時だけ入力を開く。操作の種類を色だけで伝えない。未保存入力は更新・失敗時に保持する。

電波が安定しない場合の最小代替は、本人が写真・仮ID・場所・日時・実数を控え、帰宅後に同じ商品へ照合して登録する方法。独立した第二の在庫台帳にはせず、仮記録を本登録へ対応付ける。初回からオフライン自動在庫更新や画像認識は実装しない。

## 7. 異常・見直し・通知

| 状況 | 判定の条件と必要な対応 |
| --- | --- |
| 販売可能0なのに販売中 | 対象在庫群・出荷条件・鮮度が確認済みの場合だけ確定。本人へ停止等の確認を案内する。単なる取得分0は未確定 |
| Amazonで1個以上の注文/販売を確認 | 在庫が大量/少数のどちらでも今回数量と紐付け後累計を表示。併売継続/停止を本人が判断する。停止や値下げは自動実行しない |
| 正のままFBA数量が減少 | 確認範囲/時刻の揃った数量差を表示。販売根拠がなければ理由未確認。1個売れたと断定しない |
| 在庫ありで未出品/終了/停止 | その販路で出す予定がある場合だけ出品漏れ候補。意図的な未出品・様子見・方針未設定とは区別 |
| FBA0・手元に補充候補 | 同じ状態/セットの使用可能分・未引当を確認し、FBA納品可否を別表示。候補通知であり納品作成ではない |
| 数量/状態の不一致 | 出典・観測時刻・取得範囲・移動中・注文反映を見せ、照合する。古いCSVとの不一致だけで自動補正しない |
| 販売テスト期限/再確認日 | 有効な開始日と期間があるものだけ。売上範囲不足は判断材料不足として案内する |

問題の識別は商品/在庫群+場所/販路+問題種別を基本とし、初回・継続中・解消・再発を記録。既存の通知抑制・送信待ちを再利用するが、同ASINの複数出品を独立在庫として通知しない。取得失敗中は最後の確定状態を保持して「確認不能」を重ね、復旧だけで売り切れ解消にしない。

初回は画面とプレビューのみ。固定先Gmailと現在コードの30分間隔を確認したが、第4問の回答により追加機能の販売確認は60分に改める。新しい販売のある回だけ、その回の商品を1通にまとめる。現コードの新規登録1組1通・状態確認1回1通とは区別する。実装と実送信の有効化は別途承認。登録完了メールのまとめ登録1通化は未実装の提案として残す。

販売通知は同じ問題の継続通知ではなく、新しい注文/数量の事実ごとに識別する。同じ商品でも別注文は省略しない一方、同じ注文を次回確認で繰り返し送らない。同期間の販売と在庫変化は同じ商品欄にまとめられるが、因果関係が未確認の数量差を全て販売に帰属させない。販売通知は第4問で1時間の確認1回分を1通、販売なしは送信なしと確定。既存の送信失敗の安全な再試行と、新しい販売の二重通知は別に扱う。

現行ローカル版の定期確認はPCとサーバーが動いている間だけで、現コードは30分のまま。追加設計は第6節のクラウド基盤でPC非依存・60分の確認を提案する。設定/スケジュール・排他・取得再開位置・通知済み記録はDBへ残し、クラウド再起動/多重起動も試験する。稼働開始はまだ承認されていない。クラウド化後も取得遅延/障害等で通知まで1時間以上かかり得て、売り越しを完全には防げない。販路数量の自動変更・停止は別段階。

## 8. Amazon販売テスト・楽天中古作業・滞留抽出

### 販売テスト

ASINだけで仮登録でき、ヤフオク未出品でも対象にする。SKU/状態が未特定なら数量・販売実績の確定評価を保留する。「登録/納品準備 -> 販売可能待ち -> テスト中 -> 見直し待ち -> 本人判断 -> 次回確認」の状態を持つ。

起点は実際の自社対象出品の販売可能日。BUYABLEと対象FBAの出荷可能な観測等を照合する候補だが、どの条件で開始とするか実サンプルで決める。FBA入荷前の先行購入可能状態等を通常の在庫販売と誤認しない。過去の正確な日が分からなければ本人の根拠付き入力、または未開始/要確認。時刻不明を登録日で埋めない。

開始後に販売不可になった期間の扱いは未確定。初回案は暦日と確認できた販売不可区間を別表示し、自動で期間を延長/リセットしない。補充や再出品でも同じテストを無断再開始しない。期間は商品ごとに入力し、7/14/30日は候補で固定基準ではない。

新品はAmazon継続・広告検討・ヤフオク併売検討等、中古は最初から併売/様子見後の併売を選べる。楽天新品の既存クロスマ運用は独立して継続する。期限到達で継続/併売/価格見直し/保留を本人が選び、理由と次回日を残す。売上ありでも自動で他販路を止めない。

### 楽天中古の補助

選択 -> ASIN一括コピー -> クロスマの登録入口を開く -> 本人が写真/商品情報を編集 -> 本人が登録 -> 出品結果を確認、の段階を保持する。件数は固定5〜6件にせず、実画面の入力仕様に合わせる。

ASINはコピー時に重複を除けるが、元のSKU/状態を同一商品へ統合しない。同じASINに複数の中古SKUがある場合は写真・状態の照合を促す。「コピー済み」「作業中」「本人が登録済みと報告」「URL/結果確認済み」を分ける。クロスマの商品登録だけでは楽天公開完了にしない。誤選択/失敗は再開位置を保つ。

クロスマの併売/専売、SKU対応、発送方法、楽天の公開状態、在庫連動設定を中古1例・新品1例で読み取り確認する。クロスマ/楽天APIの利用可否は未確認なので、自動API連携を約束しない。当初は承認された入口リンクと本人確認で成立させる。

### 滞留候補

プライスター現在庫CSVに、必要なら注文CSV/確認できる販売履歴を照合。原本・元列・SKU原文・時刻・取込範囲を保持し、「抽出 -> 選択 -> 監視/販売テストへ追加」のプレビューを作る。全在庫CSVを判断用に読むことと、FBA APIで全在庫走査することは別。取込だけで全件を監視登録しない。

別項目: 指定期間の販売0 / 最終販売からの日数 / 現在庫の保管期間。販売履歴の期間が足りなければ「対象期間内の記録なし・全期間不明」。在庫0/観測欠損/CSVに行なしを同一にしない。

価格・数量・新品中古・大型/高額・併売有無で絞る。大型/サイズが取れなければ本人タグを使う。在庫1〜2個や高額品を除外しない。30〜40日、2,000〜3,000円、30万〜40万円は本人の例であり、自動値下げ・返送条件ではない。返送/古物市場売却は「検討」「本人手配」「結果確認」の区別から始め、返送依頼を作らない。

### 価格・利益判断の関連案

今回の必須範囲には含めない。共通化するのはアカウント/SKU/ASIN/状態、元CSVと取得時刻、対象タグ、原価/現価格/費用の出典、本人判断の参照。将来は別案の「全行判断用」と「承認済みアップロード用」を分けたまま連携する。最低利益・値下げ幅・競合比較をここで決めず、価格更新API/アップロードを追加しない。

### フェーズ1の完了を一括で表現しない

1. 保存確認: 既存15組が維持され、商品と両ページの対応が本人の意図どおりである。
2. 送信経路確認: 既存1組のテストメールが本人に届く。これだけで在庫監視も完成したとはしない。
3. 判定確認: 自社SKU/状態、FBA取得分、出品状態、取得失敗、終了/再出品を少数例で確認する。未照合・MCF未確認等は要確認のまま残し、確定在庫切れとして送らない。
4. 監視試行: 本人が送信内容と対象を確認してから定期確認を有効化する。発送依頼・停止・再出品は引き続き本人が行う。

そのため「メール送信テスト済み」「判定確認中」「定期確認オフ/試行中」を分けて案内する。メールが一通届いたことをもって全機能の運用完了としない。

再スタート時の追加案は、第0節の再出品検討一覧をフェーズ1の見せ方へ反映すること。現在ある通知の確認と、新しい一覧/現在価格取得/自動再出品追跡の追加実装を混ぜない。追加範囲は本人確認後に限定して着手し、コンテナ管理以下の優先順位を黙って入れ替えない。

本人の販売通知/累計履歴の要望により、フェーズ1を既存経路確認の1Aと追加機能の1Bに明示して分けた。1Aのメール到着をもって1Bも完了したとはしない。1Bに必要な注文/販売の読取検証は、後段の滞留抽出まで先送りしない。52既存テストに新しい販売/履歴要件の合格実績があるとは扱わない。

## 10. 既存機能を保つ実装・保存方針

1. 本人承認後に、当日の紐付け・下書きQ・設定・履歴をバックアップ。今回の15組/58件に加え当日の変更も確認し、件数・ID・メモ・旧ID履歴で前後比較する。秘密情報を設計文書/リポジトリへ複製しない。
2. フェーズ1Aの既存経路確認はJSONとAPIのままで行える。DB移行をそのメールテストの前提にしないが、PC不要の本番構成ではDB/APIをクラウドへ移す。旧監視JSONは別に保全し、バックアップ/原文との比較から復旧案を提示し、無断修復しない。
3. 数量残高+履歴+冪等キーをトランザクションで保存する。承認済みの空の専用Neon DBを使い、アプリ用権限・接続方式・今後の費用を確認して、隔離した試験先と版付きマイグレーションで検証する。ローカルSQLiteは試験等の選択肢に限り、PC不要要件を満たす本番の代替にはしない。今回完了したリソース操作は第0節のDB作成だけで、接続/テーブル作成/移行は別承認後。
4. 現物台帳の正本は一つ。FBA/プライスター等の観測や旧JSONは取込元/履歴として参照する。移行後の同じ現物残高をJSONとDB両方へ人が更新する運用は作らない。
5. 既存のlink ID・出品履歴・メモを残し、管理商品IDへの対応を追加する。未照合は未照合として保持する。手入力メモを外部説明で上書きしない。
6. 既存JSON保存は一プロセス内の直列化のみ。スマホ/PCの重複確定と古い版の上書きは、取引ID/版番号の追加で防ぐ。履歴は修正記録方式とし、数量だけを書き換えない。
7. 移行はバックアップ -> コピーで変換 -> 差分プレビュー -> 件数/識別子/数量/履歴検証 -> 承認後に更新を一時止めて最終差分/切替。ローカル/クラウドの両方で書き続けない。旧/新のスケジュールとメールを同時稼働させず、送信済み/結果不明も引き継ぐ。切戻し時も処理済み取引/送信の重複を防ぐ復旧手順を先に用意し、確認未完の旧監視を勝手に統合しない。
8. クラウド移行時は数量/履歴/操作IDと必要な送信待ち登録を同じ取引にまとめる。外部メールの送信そのものはDB取引の外で行い、受付/失敗/結果不明を保存する。関数が途中で止まっても未保存の成功や無条件再送を作らない。試験環境は本番の送信権限/定期実行を継承して動かさず、必要最小のデータだけで検証する。
