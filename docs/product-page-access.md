# 商品ページへの直リンクとURL登録

## 2026-11-03 登録済みの商品を選んでつなぐ

1. カードの「ヤフオク URLを登録」または「URL登録・修正」を開く。
2. 「登録済みの商品から選ぶ」を押す。同じASINを初期検索にし、商品名・ASIN・SKU・出品IDでも探せる。写真、SKU、新品中古/ランク、出品IDまたは場所別数量、メモを確認する。
3. 対象を選ぶと確認欄へ切り替わる。「この商品と関連付ける」で保存。選択だけでは保存せず、「選び直す」「×」「取消」で戻れる。見つからない場合は選択窓を閉じ、従来の新規URL入力を使う。「商品紐付けツールを別タブで開く」も併設し、作業中の画面を残す。

在庫/販売見直しからは登録済みの紐付け出品を選ぶ。商品紐付けページからは逆に、登録済みのコンテナ・自社在庫を選べる。全商品一覧も同じ共通部品を使う。同じASINというだけで選択/統合せず、関連付け済みや明らかなASIN/SKU/状態/セットの相違は選択不可または保存時に拒否する。SKUが空の在庫へ異なるSKU/中古ランクの複数出品をまとめない。

`kind: associate-existing` と `targetKey` を本人の確認操作で送り、既存3文書のトランザクションで元/先の保存世代、ASIN、SKU、状態、セット、確認済みリンクを検査する。最新の自社FBA観測からSKU/状態を解決し、古いカタログだけで誤判定しない。保存するのは既存ID間の関連と操作履歴だけ。現物残高・商品メモ・SKU・既存URL/リンクID・計画の販売可能日/期間/判断は変更しない。競合は選択を残して再確認し、応答消失は同じ操作IDで照合する。外部出品/価格/在庫・メールは操作しない。

再検証：`node tests/review-picker-browser.mjs`。元メモと数量を持つ別タブ、選択/検索/該当なし/取消、在庫↔出品/計画→出品、競合/応答消失、320～1440px、重複商品/数量/日付不変を隔離メモリDBで確認する。

2026-11-03：4画面のカードに「紐付け・実在庫・販売見直し・全商品」と補充条件への共通導線を追加。FBA/ヤフオクだけでなく関連したコンテナ/会社も常設し、未関連候補の数は確定数量に使わない。[商品の共通参照とFBA優先補充](product-workspace.md)。

## 2026-11-03 販売中なのに数量が未確認になる場合

- FBA数量が「未確認」の場合は、カード右上の数値（鉛筆付き）を押し、数量だけ入力して「FBA数を保存」。SKUの指定は不要。「FBA数量・手入力」と本人確認日時を表示する。0は在庫なし、空欄保存は手入力を解除して自動取得/未確認へ戻す。これはこのツール内の確認値であり、Amazonの数量や現物台帳を更新しない。
- 数量だけの保存はkind=manual-fbaを既存の取引・本人確認・保存世代・操作IDで処理する。SKU/紐付け、現物数量/メモ/イベント、計画の日付を更新しない。確認履歴は既存inventoryReviews/inventoryReviewHistoryへ残す。
- 数量専用入力は確認日が古くなっても保存値を消さず「要再確認」を付ける。26時間超やSKU未選択の手入力を在庫超過の確定比較には使わず、別SKU/新品中古へ流用しない。自動取得数が一意に確定した場合は自動値を優先。通知・補充判定の原観測を手入力で取得成功扱いにはしない。
- 販売状態と数量を分ける。Amazonリンクに「FBA数量」と「FBAで販売中」を併記し、複数SKUで数を決められない場合は「対象SKU未選択・候補n件」を表示する。販売中の商品を未出品と扱わない。
- 自社発送のみの自社出品は「自社発送販売数」と「自社発送で販売中」を表示し、FBAの出品登録がないことを小さく併記する。この販売可能数はListings Items APIのDEFAULTのfulfillmentAvailability.quantityであり、FBA販売可能数やコンテナ/会社の実数とは別。該当SKUが複数の場合は合計せず数量未確認とする。
- SKU確認画面は候補を常時表示する。各候補のSKU・新品中古のランク・販売中/停止中・FBA販売可能数・自社発送販売数を確認して選ぶ。新品の在庫へ中古SKUを選ぶ操作は許可せず、自由入力でも取得済みの状態差異を表示する。SKU選択だけでは保存せず、本人の保存操作が必要。
- 学研の例は新品の販売中SKUと旧SKUが同時にあり、数量を自動合算しなかったため未確認だった。対象SKUが分からなくても数量の手入力で確認値を表示でき、SKU選択は必須ではない。Dellの例は自社発送の販売中出品であり、FBA数量がないだけで未販売ではない。
- 手入力はFBA未取得時の補助。自社発送のみと確認できたSKUではFBA数の入力を出さない。SKU変更時は入力欄の前の手入力数を消して持ち越しを防ぐ（元の記録は保存するまで変更しない）。空欄と0は区別する。
- 自社出品の取得結果はASINの確認範囲ごとに最新を選び、従来の「Amazon自社出品を確認」で得た結果も共通カードへ反映する。新しい失敗は未確認とし、過去の成功へ黙って戻さない。別ASINだけの新しい取得でこの商品の正常な結果を隠さない。
- 本人からの指摘には商品名/ASIN、FBAか自社発送か、自社販売元の分かる画像があれば足りる。商品ページの別会社のカート数量は自社数量の根拠に使わない。画面を見ただけでSKU・実数・販売確認を代理保存しない。

一次資料：[Listings Items APIのライブ数量](https://developer-docs.amazon/sp-api/docs/listings-items-api)、[searchListingsItemsのBUYABLEとfulfillmentAvailability](https://developer-docs.amazon/sp-api/reference/searchlistingsitems)、[FBA Inventory API](https://developer-docs.amazon/sp-api/docs/fba-inventory-api)。販売中はBUYABLE、FBA数はFBA InventoryのfulfillableQuantityから判定する。今回の自社発送数の表示は、自社発送の在庫切れ通知機能まで完了したという意味ではない。

再検証：`node tests/amazon-status-browser.mjs`。隔離メモリDBで新品97/旧SKU0/中古6、自己発送2/実物3+1、SKU明示選択、手入力の切替、別タブの新規/既存見直し、320/390/800/1440pxを検査する。取消ボタンの共通属性が実在庫画面の処理と干渉しないことも含む。

数量専用入力と上部タグの再検証は `node tests/manual-fba-membership-browser.mjs`。SKUなしで92/0/空欄、再読込、競合時の入力保持、応答消失後の同一操作照合、登録先1/2/3か所と候補の区別、4画面の共通表示、320～1440px、現物/メモ/日付不変を隔離メモリDBで確認する。本番の数は本人だけが入力する。

## 2026-11-03 数量・SKU・出品終了の表示

- AmazonリンクにはFBA販売可能数、ヤフオクリンクにはその出品の販売数を表示する。FBA総数、予約・処理中、追跡後注文、現物在庫、MCFの発送可否とは別の値。Amazon自社発送の販売可能数もFBAとして扱わない。
- ヤフオク終了を検証できた場合は赤い0個。ページ内に古い正の数量が残っていても販売数に使わない。FBAが正なら「再出品を確認」と表示する。404・取得失敗・古い情報は未確認のままで、0個や終了としない。
- 同じASIN・SKUを使うヤフオク出品は、出品IDの重複を除いて販売数×unitsPerListingの合計をFBAと比較する。一部未確認でも既知分だけで超過すれば警告し、未確認が残る間は安全と断定しない。異なるSKUは合算しない。同じSKUのFBA記録が食い違う場合も要確認。
- SKUと中古の詳細ランクを表示する。「SKU・在庫数を確認」で自社SKU候補（状態とFBA/自社発送別）を選ぶか手入力する。明示的な在庫・計画の関連付けとSKUが食い違う場合は別行として保持し、ヤフオクは「比較対象外」と表示する。SKU不明の現物へ異なるSKUの計画を推測統合しない。
- 「FBA在庫の手入力」はAmazonの値を取得できない場合の補助。空欄は未確認、0は在庫なし。取得できたAmazon数量が優先。従来のSKU確認フォームの補助値は26時間で期限切れ、数量専用フォームは期限後も確認日付きで保存値を表示するが比較には使わない。保存したSKUと異なるSKUへ転用しない。SKU未選択で複数の状態がある場合、手入力だけでは比較を確定しない。
- 確認時刻・予約/処理中・複数出品の必要数・MCFに関する説明は「確認時刻・補足」へ、注文履歴は従来の補足へ移す。コンテナ・自社在庫と全商品一覧ではFBA／ヤフオク／コンテナ／会社・自宅を別表示する。
- タイルは在庫欄を切らない高さとし、これらの在庫付きタイルは600px以下で1列にする。既存の並び替え、URL編集、現物数量の編集は維持する。

保存先は既存3文書。選択SKUはlinkのamazonSellerSku、stock/planのsellerSku、補助値はlink-monitor.inventoryReviewsへ記録し、置換前をinventoryReviewHistoryへ保存する。操作IDによる再試行、保存世代、本人・同一Origin、読み取り専用、トランザクションの検査を維持する。外部の出品・価格・在庫は変更しない。

## 目的と操作

商品紐付け、コンテナ・自社在庫、販売の監視・見直しの各リスト/タイルの表面に「Amazonを開く」「ヤフオクを開く」を表示する。詳細展開を要求しない。未登録は「Amazon URLを登録」「ヤフオク URLを登録」を同じ場所に表示し、URL入力へ直接進む。

- Amazonは既存ASINから正規の商品URLを作る。URL未登録の在庫/手入力計画はASINまたは商品URLを登録できる。既存の別ASINへの差替えは商品情報の訂正として扱い、このURL編集では拒否する。
- ヤフオクは登録済みURLを開ける。自動取得に失敗してもリンクを隠さず、「登録URLを開くかURLを修正」と表示。未登録/登録直後/出品中/終了/取得失敗を区別する。取得失敗を終了や0個と扱わない。
- 「URL登録・修正」で出品を追加、または既存出品URLを変更する。変更時は紐付けIDを維持し、参照している在庫/計画へ反映する。古い出品記録/URL変更履歴は保存する。前の写真を参考にする場合は以前の出品写真と明記する。
- URL登録は監視対象にも反映する。手入力計画への出品追加は明示的なlinkedLinkIdsとして保存し、同ASINだけの推測統合をしない。数量・販売可能日・方針・期間・既存メモを作り直さない。
- 「状態を再取得」は登録商品のFBA/ヤフオクをメール送信なしで取得する。従来の日次確認で保存された新しいFBA/自社出品/ヤフオク結果を、3画面でも表示する。取得範囲・SKU・状態・鮮度が解決できない数量は再取得や登録の操作を示す。
- 場所別数量の空欄は実数未入力と表示し、在庫タイルから数量入力を開ける。0と同じ扱いにしない。

## 保存と検証

既存のlink-monitor/physical-stock/sales-planningの3文書を同じDBトランザクションでロックし、変更文書だけ更新する。途中失敗は全体をロールバック。URL変更と在庫/計画への関連付けを別々に確定しない。DDL・権限変更・新DBは不要。

本人認証、同一Origin、閲覧権限、監視文書と対象文書の保存世代を検査。操作IDと本文のハッシュで再試行を識別し、COMMIT応答消失後も同じ操作の保存を再確認できる。競合時は入力を残して最新版を取得し、保存前の再確認を求める。外部リンクはAmazon/ヤフオクのHTTPS正規URLだけ、別タブにはnoopener/noreferrerを付ける。

テストは架空の隔離データで、各画面のタイル直リンク、未登録からの保存/再表示、URL訂正と元ID/数量/日付維持、ASIN/URL/状態不一致拒否、途中失敗の全体ロールバック、応答消失、権限/Origin/競合を検証する。本番へ架空出品を保存しない。最新の配備・確認結果はstatus.md。

在庫表示の再検証は `node tests/inventory-visibility-browser.mjs`。先に `npm run build:cloud` を実行する。PLAYWRIGHT_MODULEは既存の利用可能なPlaywrightへ指定できる。メモリ内の隔離サーバーだけで数量表示・SKU不一致・手入力0/空欄・再読込・保全・320/390pxの1列と横はみ出しを確認し、終了時にサーバーを停止する。

## 依存監査の別残件（2026-11-03）

`npm audit --omit=dev` は9件（critical 1、low 8）を報告した。better-authの [Magic Link/OAuth検証レコード混同](https://github.com/advisories/GHSA-965c-763c-88jm)、[OAuth Proxy](https://github.com/advisories/GHSA-r4xp-prcw-77qf)、[Drizzleのレート制限](https://github.com/advisories/GHSA-44jh-23m7-hpcf)、および [deepmerge](https://github.com/advisories/GHSA-gcqx-w48m-w2h4) とその間接依存である。

本アプリのソースはNeonの認証クライアントとリモートJWKS/JWT検証を使用し、Better Authサーバーを起動しない。配備関数内にbetter-auth/Drizzle/deepmerge/html-to-textのファイルがなく、同じ設定で取得したブラウザビルドの入力にも対象サーバーハンドラー・Drizzle・deepmerge・メール描画が含まれないことを確認した。クライアント用Magic Linkモジュールとサーバーの脆弱ハンドラーを区別する。Neon管理側の実バージョン/有効プラグインは今回確認しておらず、安全確認済みや監査合格とは報告しない。強制依存更新やログイン方式の変更はせず、管理サービス側の影響確認とSDKの互換更新を別残件にする。
