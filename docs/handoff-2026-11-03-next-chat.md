## 目的と運用の確定事項

単なるAmazonからヤフオクへの自動出品ではなく、「どこに何が何個あり、どこで売っていて、次にどう売るか」を一つのツールで判断する。別台帳を増やさない。まず検知・一覧・通知と本人判断を優先し、実行の自動化は急がない。

- 基本はFBA在庫をAmazonとヤフオクで併売。ヤフオク注文のAmazonマルチチャネル発送依頼は本人が1件ずつ入力している。自動発送は必須ではない。
- コンテナ在庫は約9割がFBA追加納品用。ただしコンテナも直送に使うことがある。会社/自宅はFBAへ入れられない自己発送品も多い。
- ヤフオクは自動再出品約3回。売れ残り時はAmazon在庫と売れ行きを見て、値下げ/再出品を本人が判断する。
- Amazonでよく回るようになればヤフオク併売をやめることがある。連携解除と実際のヤフオク販売停止は別操作であり、解除だけで販売停止したとは扱わない。
- 注文通知は注文確定時を希望。1個の販売も履歴に残し、売れていないときは送らない。希望として1時間集計があったが、現在の実稼働は本人選択の午前9時台の日次確認。希望と現状を混同しない。
- 実在庫入力はまず本人1人が手動。スマホ回線で外出先から利用し、PCでも扱いやすくする。自宅PCの常時起動を前提にしない。
- Vercel + 専用Neonで保存/認証。日常利用は本番URLだけで、PowerShell起動は不要。旧OneDriveのローカル版は正本ではない。
- 別のNeon既存プロジェクト（Indigo Lighthouseは使用中の別ツール等）を変更/削除しない。Netlify新規登録も不要。

## 絶対に維持するデータの区別

- ASINは共通カタログ。自社のseller、SKU、新品中古、状態ランク、付属品/セット違いを区別し、ASINだけで現物を合算しない。
- 保管場所（コンテナ/会社・自宅/FBA）と、販売先・発送方法（Amazon FBA/自己発送/ヤフオク/楽天等）は別概念。
- 同じ現物の併売・ページへの登録で実在庫を増やさない。各画面は元の商品/実在庫/計画を共通参照し、「移動」は元ページから削除する意味ではない。
- FBA総数、販売可能数、MCF注文へ実際に充当可能な数を同一視しない。未確認、取得失敗、古い情報、未登録、0個は別。
- Amazonのカートを他社が取っていても自社出品を読む。他社カート数量を自社在庫として取り込まない。販売中でもSKU未選択なら数量は未確認になり得る。
- 手入力FBA数は本人確認の値として確認日時と区別し、取得成功とは扱わない。97等を勝手にAPI値へ戻さない。
- 数量を「3個追加」と「実数を3個に修正」は別操作。理由/前後/場所/日時/操作IDを残す。注文/CSV/保存再試行の二重増減を防ぐ。
- 移動は出荷元→移動/納品中→受領を追い、二重計上を避ける。予約/使用不可/未確認は自由に使える在庫へ足さない。
- 販売テスト起点は登録日/発送日でなく実際の販売可能日。広告開始日はさらに別。写真/メモやASINだけで販売開始日を推測しない。

### 最新UXの必須仕様（何度も指摘されたため後退禁止）

1. 商品カードから他の関連ページへ開くリンクは `target="_blank" rel="noopener noreferrer"`。今の選択/検索/スクロール/編集中タブを残す。全体ナビと商品別リンクを区別する。
2. 在庫の「紐付けを登録」は `/#stock=<id>&edit=1` の新規タブで、写真/商品名/ASIN/メモ/数量を引き継いだURL入力を直接開く。元の商品を探し直させない。
3. 「ヤフオク URLを登録」「URL登録・修正」には新しいURLだけでなく「登録済みの商品から選ぶ」がある。選択時点では保存しない。SKU/状態/セットを照合し、保存後に紐付けページへ反映する。
4. 同じURL画面で「販売見直しにも追加」をチェックすると、紐付けと見直しを1回の保存で追加。既存計画は再利用し、日付/メモを上書きしない。数量を複製しない。
5. URL未登録でもカードの「見直しに追加」で、その場の小さな入力から元商品参照を登録できる。ページ移動なし。見直しページを開くリンク自体は別タブ。
6. 登録済みの青（紐付け）/緑（在庫）/黄（見直し）タグは上部。未登録なのに所属済みの色タグを付けない。
7. 見直し一覧は5列/約358pxのタイル、密なリスト。写真/名前/4数量/状況/確認日/方針/メモ1行を中心にする。全文/SKU操作/履歴は「詳細」。主要一覧へ以前の長い操作群を戻さない。
8. コンテナ在庫カードのメモは意味を伝えるためのもの。カード上で表示・編集できる状態を維持。販売見直し側の長文は詳細へ。
