# Amazon販売履歴・手動確認

## 2026-10-31：対象拡張と取得遅れの追加方針

追加設計の正本は `inventory-integration-design.md` 冒頭の10月31日追記。現コードの `cloud-sales.js` はヤフオク紐付けとFBA取得結果から一意なSKUを選ぶため、コンテナ・自社在庫だけに登録した商品やFBAでSKUを特定できない自己発送品は、登録しただけでは追跡対象にならない。注文読取側はFBA/自社発送を区別する部品を持つが、全自己発送品の追跡対応済みとはしない。

次の実装では、登録対象の自社Amazon出品からSKU/状態/発送方法を解決し、ヤフオクの有無やFBA在庫取得に依存せず追跡できる形へ拡張する。複数SKUは本人確認、同じSKUの複数出品や在庫/計画両方への登録は注文を二重計上しない。既存追跡開始日と履歴は保持する。ASINだけでは注文を紐付けない。

本人添付の画面は確認末尾が10月26日01:21:36で遅れを表示。HP販売1件/自社発送、学研/Dell等の販売は本人申告であり、今回実注文照合は未実施。最新の取得済み期間と対象SKUを先に確認し、現行の7日/5ページ/40秒/取得間隔に沿って不足を解消する。上限超過時の期間分割・再開は拡張し、途中失敗や対象不明を販売ゼロと表示しない。

過去の補完と通知開始後の新規販売を分け、過去分を一斉送信しない。販売通知の追加は現物数量の自動減算を意味しない。全件登録ではなく少数の試用から進め、既に受信確認した架空メール試験を繰り返すのでなく、実注文と通知経路を段階別に確認する。

2026-10-26の追加。進捗は [status.md](status.md)、通知の稼働範囲は [notifications.md](notifications.md)。1時間通知の前段として、既存の本人限定画面/DBへ追跡開始・注文読取・履歴・通知プレビューを追加する。別の台帳/DB/認証は作らない。

本番へ配備し、01:21:27日本時間から15組/14 SKUの追跡を開始した。01:23:37の初回確認で01:21:36までの取得が1ページで完了、当該短区間の新規注文0件。接続・空応答・保存・表示の成功を確認したが、実注文がある応答や実キャンセルはまだ未確認で、模擬試験の合格と区別する。メール記録は既存テスト1件のままで追加送信なし。

## 操作

1. 本番URLで本人ログインし、必要なら「FBA在庫を確認する」で自社の対象SKUを確認する。
2. 一覧の下の「Amazonの販売履歴」で「販売追跡を開始」を押す。開始時刻をDBへ保存するだけで、注文取得・メール・在庫変更は行わない。同じ操作で既存の開始時刻や履歴をリセットしない。
3. 約2分以上経ってから「注文を確認」を押す。登録対象へ対応するSKUの販売履歴を保存し、商品行に取消除外の確定数量を出す。開始前の販売を推定して足さない。既存紐付けの登録日と、この新しい追跡開始日は別である。
4. 「販売履歴・通知プレビュー」を開き、今回の注文確定/取消・訂正、商品、両ページのリンクを見る。再取得だけでは同じ注文を追加しない。実メールは送らない。
5. 後から紐付けた商品は「未追跡の商品を追加」。追加時刻から追跡し、既存商品の開始日は維持する。複数SKU/状態不明は勝手に合算せず未追跡/要確認とする。

PC/スマホは同じ画面。スマホ幅の模擬画面試験と、本人がPCを切ってスマホ回線から操作する実機試験は区別する。

## 何を数えるか

- Amazon注文の `UNSHIPPED` / `PARTIALLY_SHIPPED` / `SHIPPED` を確定の根拠にする。未確定は加算せず、出荷への変更だけで再加算しない。
- 同じアカウントの注文ID+明細IDを同じレコードとして更新する。ASINだけでは足さず、SKU別に分ける。同じSKUにヤフオク2出品があっても、通知プレビューの注文数は1回だけ集計する。
- 初めて確認した確定注文で、注文作成が追跡開始前なら過去分の補完扱いとし、今回の新規販売へ加算しない。追跡開始後に未確定を観測し、その後確定を観測できた旧注文は確定時の観測から対象とする。観測日時を実際の注文確定日時と断定しない。
- 明示的な注文全体のキャンセルは履歴/累計を訂正する。キャンセルの申請だけでは取り消さない。明細だけのキャンセル実行、重量販売、関連注文/交換、状態不明などで数量を確定できない場合は要確認にする。確定済み注文が未確定へ戻った場合も、勝手に取消としない。
- `NON_AMAZON` は除外し、MCF発送をAmazon販売へ数えない。販売情報でFBA観測数や現物在庫を再減算しない。返品・返金の自動在庫戻しは未実装。

## 取得と保存

Amazon Orders API v2026-01-01の `searchOrders` を日本市場・更新期間で限定する。`includedData` は `FULFILLMENT,CANCELLATION` のみ。購入者/住所/金額のデータセットは要求せず、商品名・シリアル・生レスポンスも保存しない。対象外SKUはメモリ内で除外し、DBへ残さない。APIにはSKUでの直接絞込みがないため、日本/短い更新期間内の注文一覧を受けて照合する方式であり「Amazonが対象SKUだけを返す」とは説明しない。

同じ `link-monitor` 文書の任意項目 `salesTracking` に、追跡対象/不変の開始時刻、必要最小限の注文情報、差分イベント、取得済み期間、ジョブID/期限を保存する。行ロック/版番号と既存のDB権限を再利用し、追加DDLは不要。秘密設定は既存の専用Vercel設定を使い、値を再入力/再公開しない。

1回の取得は最大7日/5ページ/40秒。上流の2分以上前を期間末尾とし、5分重複させて更新を読み直す。全ページ成功時だけ期間を進め、上限/失敗/中断では完了済みや販売ゼロにしない。注文の変更日時が古い結果は現在の取消を戻さず、同じ更新時刻の矛盾は保存しない。長い未取得期間は残期間ありと表示する。大量注文でページ上限に当たる場合の期間分割/再開拡張は残件。

取得前にDBへ60秒の実行リースを保存し、同時実行を抑止する。対象/アカウント/SKUが変わったら旧結果を採用しない。注文APIの取得間隔は約3分以上、サーバーのタイマーやブラウザを閉じた後の処理に依存しない。保存結果不明を無条件再実行しない。注文1万明細/イベント2万件を超えると停止し、過去履歴を黙って削除しない。

本人限定の `POST /api/link-monitor/sales/start` と `POST /api/link-monitor/sales/check` は同一Origin、JSON、`If-Match`必須。クライアントに任意アカウント/SKU/期間/注文データを指定させない。画面/ログに認証情報や上流の生エラーを出さない。

- ヤフオク状態の実再取得/後継の自動検出、出品停止、再出品、値下げ、MCF発送依頼、現物台帳の増減。
- 過去の紐付け日まで遡る販売履歴の復元、クロスマ/プライスターの二重処理調整、返品/部分取消の自動確定。
