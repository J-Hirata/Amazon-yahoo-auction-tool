# 販売の見直し

進捗の正本は [status.md](status.md)、全体設計は [inventory-integration-design.md](inventory-integration-design.md)。2026-10-27の最小版は、登録した商品の「何を試すか」「いつ確認するか」「次にどうするか」を本人が記録する。滞留自動判定、広告や価格の実行、自動通知をまとめて完成扱いにしない。

## 入口と操作

本人ログイン後の上部「販売方針 → 販売の見直し」、または https://amazon-yahoo-inventory.vercel.app/?view=planning 。コンテナ・自社在庫や併売ツールを置き換えず、同じ認証・専用DBの中に追加する。PC/スマホ両対応。

1. 「商品を追加」で、既存のコンテナ・自社在庫、既存のAmazon/ヤフオク紐付け、または手入力を選ぶ。既存全商品は自動登録しない。
2. 商品名、新品中古、任意のASIN/SKU/セット内容を確認する。ASINだけの仮登録も可能。ASIN未作成の商品も名前から登録できる。既存参照では同じASINでもSKU・状態・セットを混ぜない。
3. 取り組みを「Amazonで様子を見る」「広告テスト」「販売方針の見直し」から選ぶ。期間は初期14日だが商品別に1〜365日で変更する。14日を固定の滞留判定や値下げ条件にしない。
4. Amazon様子見の起点は、実際に対象商品が販売可能になった日と本人が確認した根拠。納品準備/発送/登録日から自動開始しない。不明なら空欄のまま開始待ち。
5. 広告テストは販売可能日とは別に、実際に広告を開始した日を記録する。この入力で広告は開始しない。これから広告を検討する作業は「販売方針の見直し」と次回確認日で予定化できる。
6. 「保留」または「販売方針の見直し」には任意の次回確認日を設定する。完了は一覧の「完了」に残し、削除しない。
7. 次の方針（Amazon継続/広告/ヤフオク/楽天/価格見直し/返送等/保留）、販売実績メモ、判断メモを保存する。これらは本人判断の記録であり、本番操作ではない。

保存後は一覧を再読込し、確認日/状態/メモが残ることを確認する。期限は一覧取得時に日本時間の暦日で判定し、今日または過去なら「見直し時期」。ページを開いただけでメールを送らず、期限のメールリマインダーもまだない。開始後の販売不可区間や補充で自動延長・リセットしない。

## 一覧と参照の境界

- 写真/商品名/新品中古/ASIN/SKU、取り組み、開始日、確認期限、残日数/経過日数、次の方針を表示する。
- 数量は明示的に選んだ元の商品IDからの参照のみ。コンテナ/自宅・会社/FBA取得分を合算しない。古いFBAや未取得は未確認であり0ではない。取得分はMCF出荷可能の保証ではない。
- ASINだけの手入力を同ASINの現物へ自動関連付けしない。参照先のIDがなくなった、またはASIN/SKU/既知状態/セット内容が変わったときは、数量参照を止めて警告する。判断メモや完了の記録は残せる。
- 確定済みのASIN/SKU/状態/セット/参照商品を別商品へ変更しない。仮登録の空欄/状態未確認だけは後から補完でき、同じ管理ID・登録日時を保つ。参照商品の補完は元情報との照合が必要。
- 売上実績はこの版では本人の販売メモ。既存の紐付け後注文数をテスト期間内売上や「売れていない」の証拠に転用しない。注文APIの期間/SKU別照合は後続。
- ASINコピーはコピーのみ。楽天出品完了、クロスマ登録完了、在庫連動開始にはしない。クロスマの入口・中古登録段階管理・中古連動範囲は未実装/未確認。
- 画面の判断履歴は全計画を合わせた直近100件内で表示する。保存履歴は削除せずDBに保持する。商品ごとの履歴ページングは後続。

## 保存と接続

既存 `app_storage.documents` に `sales-planning` 文書（version 1、plans/events/receipts）を1行追加する。既存3文書や既存の数量台帳を作り直さず、DDL/権限追加/別DBは不要。アプリは既存のSELECT/UPDATE限定ロールと行ロック・版番号付き更新を再利用する。本人確認/同一Origin/JSON/If-Match/閲覧専用をAPIで検査する。

`scripts/initialize-sales-planning.mjs` は通常dry-run。確認済み専用接続で `--apply --confirm-document=sales-planning` を指定した場合だけ、空文書を `ON CONFLICT DO NOTHING` で追加する。再実行で既存計画を上書きしない。開発ブランチで保存/再実行を試験してから専用mainへ同じ処理を適用する。移行時の同一トランザクション内で他文書の内容/版番号が不変と確認する。秘密の接続情報はチャットへ貼らず、既存の非公開設定を使う。

保存は操作ID/計画ID/内容ハッシュ/本人/日時を持ち、同じ操作の再送を重複適用しない。前後の計画を履歴に残す。通信で応答が失われた場合は同じ操作IDをブラウザの本人別sessionStorageに保持し、再読込後も受付確認/同じ内容の明示再試行で復旧する。確認が済むまで新しい保存を無効化する。競合時は既存判断を上書きせず最新の一覧へ戻す。

## 通知の今回の確認

在庫0（FBA取得分でありMCF在庫切れ確定ではない）→通知文→模擬SMTP受付、同じゼロの重複抑止、取得失敗の区別、復旧と再発、送信結果不明の再送保留を自動試験する。

本人の明示承認後、2026-10-27 12:49日本時間に共通Gmail送信処理を使い「【ヤフオク併売ツール】架空の在庫ゼロ・送信テスト」を1通送った。架空ASIN/出品IDとテスト商品だけで文面を生成し、実在庫/出品/価格や本番3業務文書へ書き込まない。Gmailの受付後、本人が「届いた」と回答。受付/受信確認は `data/cloud-private/zero-notification-test-v1.json` に保存しGit/配備から除外する。`scripts/send-zero-notification-test.mjs` は送信前にwx受付を作り、この1回の無条件再送を拒否する。受信確認の更新は送信せず記録だけを行う。

これは手動の架空通知が届く確認であり、実売上→1時間スケジューラー→自動メールの本番一巡ではない。本人から必要なテストメールの送信許可を得ているが、送る際は都度件名と結果を報告する。通常の自動メール/定期確認はオフを維持する。

## 残件

全在庫と販路状態の横断一覧、プライスターCSV滞留抽出、テスト期間の実注文集計/観測不足表示、販売不可区間の扱い、広告実績の取込、楽天中古の一括作業補助、期限メール、自動通知の本番スケジューラーは別工程。価格/広告/出品/返送の実行はこのページから行わない。
