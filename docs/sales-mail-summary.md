# 販売メールの商品別集計と在庫表示

2026-11-06。販売・訂正メールを注文イベントごとの繰返しから、ASIN・自社SKU・発送方法ごとにまとめる。注文確定・取消訂正・差引を分離し、日本時間の注文日（訂正は更新日）ごとの内訳を表示する。今回新たに確認した分であり、全件を無条件に「昨日の販売」と呼ばない。既送信イベントを再通知しない。

## 数量

- FBA販売可能：同じ自社SKUのAmazon取得値と取得日時。取得値は販売/予約を反映済みの場合があるため、通知された販売数をさらに減算しない。複数SKUのある同ASINでも対象SKUの値を表示する。
- FBA推定残数：既存ツールの手入力基準がある場合、基準以降のAmazon確定販売を販売追跡イベントから累積して差し引く。今回の通知に含まれない既送信分も計算し、毎日同じ基準から新着分だけ引くリセットを防ぐ。イベントIDは重複排除する。
- 手入力のSKU指定ありはそのSKU、SKU未指定は明示された同一商品の追跡対象SKU全体。対象SKUの販売追跡開始が基準より後、確認期間不足、未来の基準、SKU不明なら計算保留。マイナスの算出結果は隠さず基準数要確認とする。
- 推定は注文確定の正の増分だけを引く。取消による在庫復帰・FBA納品・他販路販売を推測で加減算しない。この限界を本文に記載する。基準更新には既存の「SKU・在庫数を確認」/FBA数量編集を使用する。
- 自社/自宅、コンテナは関連付け済みの実在庫IDごとに使用可能数を参照。重複参照は1回だけ数える。確認日時を併記し、未入力/未関連を0扱いしない。異なる単位を合算しない。FBA販売から現物台帳を自動減算しない。
- 同じASIN・SKUというだけで無関係の台帳を結び付けず、既存追跡対象のsourceId/linkIdが一致する共通商品行から参照する。

## 保存と実行

日次の注文確認→商品監視→集計メール保存→既存の耐久送信処理、の順。商品監視後の取得値を使う。在庫読取だけが失敗した場合は販売通知を止めず、数量未取得として送る。保存後の本文は再試行でも変えない。既存イベントID/メールキー/送信受付・結果不明・重複抑制を維持する。新規DB文書やスキーマ変更は不要。

推定数量はメール内の表示であり、保存済みの実在庫・FBA手入力基準・計画・出品・価格を変更しない。楽天/メルカリShopsとの在庫同期は未実装で、本人が台帳/基準を確認更新する。

## 検証

単体/隔離結合：5注文の合算、日付境界、異なるSKU/発送区分、取消・訂正、既送信分を含む累積、重複イベント/台帳、未入力とゼロ、期間不足/未来基準、負数、読取失敗、監視更新後の本文作成、再実行で同じ販売を送らないこと、整形による元データ不変。

実データの非送信プレビューでは、学研5個（11/4に1個・11/5に4個）を1商品へ集約。11/6 09:50取得の対象SKU FBA87個、手入力97個(11/3)から基準後の確定販売7個を引いた推定90個、コンテナ150個・自社未入力を表示する。旧SKUのFBA0を混ぜて対象SKUの数を変えない。数字はその時点の証跡であり現在値として固定しない。
