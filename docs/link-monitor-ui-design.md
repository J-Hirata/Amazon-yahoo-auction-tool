## 1. 目指す使い方

「AmazonのASINとヤフオクURLを入れる → 写真と名前で登録した商品が分かる → 自社の在庫と必要な対応が分かる」。通常対象は10〜30商品。Amazon全在庫の取込、SKUの手入力、毎回の確認チェックを求めない。

登録操作と、画像・在庫の取得と、メール送信は別の結果として表示する。登録が成功しても、在庫やメールまで確認済みに見せない。

## 2. 調査時点の現在地

| 項目 | 確認できたこと | 残っていること |
| --- | --- | --- |
| ASINと出品URLの紐付け | 既存機能として利用中 | まとめ登録の設計・実装 |
| FBA数量 | 登録ASINを自社出品者・SKUへ絞って手動取得する処理あり | 数量とMCF出荷可否を分けた表示。複数SKUは合算しない |
| Gmail | テスト1通の送信と本人の受信画面まで確認済み | 新規紐付け通知、送信記録・再試行、定期通知は未完成 |
| メモ・ヤフオク画像表示・チェック撤去 | 直前の変更コードは隔離テスト済み | 本番サーバー未反映。現状のコードを完成UIとみなさず本案に照らして見直す |
| 自社Amazonコメント・出品写真 | 現コードでは取得・保持していない | APIの取得候補を文書で確認しただけ。御社の実データでの取得可否・同定は未確認 |

作業中の静的ファイルと稼働中バックエンドには差がある。登録中の本人へ新機能の操作を案内しない。実装・反映を再開するときに、登録作業の区切りとデータ保持を確認する。

## 3. 画面の構成

主画面は「登録欄」「登録した商品」「要対応の通知」の3か所に絞る。既存の下書きQとの往復導線は維持する。試験メニュー・取込・ログ・技術情報は詳細設定にまとめる。

### 登録欄

- 初期表示は今と同じ2欄と「この2つを紐付ける」。確認チェックは置かず、ボタンを明示的な登録操作とする。
- 「まとめて登録」で複数行表示へ切り替える。各行はASINとヤフオクURLの2欄。「行を追加」と「まとめて紐付ける」を用意する。
- Excel等の2列貼付も候補。ただし複雑なCSV設定を通常手順にしない。
- 入力中に行ごとの形式・重複・既存登録を表示する。登録ボタンの時点で組を見渡せるようにし、確認用チェックや追加モーダルを重ねない。
- 成功行は「今回登録」、同じ組は「登録済み」、不備はその欄に理由を表示する。別ASINへ紐付いているURLは「別の商品に登録済み」として上書きしない。
- 部分成功後の再実行は失敗行のみを対象とする。成功した行や他の未入力行は消さない。1件の失敗で全成功分を戻さない。
- 登録の保存を先に完了する。画像・商品名取得は別処理とし、通信失敗で登録が失敗したように見せない。

### 登録した商品

PCは比較しやすい一覧。1行の主な情報は以下とする。長いURLをそのまま表示しない。

| 商品 | 御社のAmazon | ヤフオク | 自分用メモ |
| --- | --- | --- | --- |
| 写真＋商品名 | FBA 9個（取得分）／確認時刻／Amazonリンク | 出品ページのリンク／確認できた出品状態 | スタンドなし［編集］ |

- 写真の出所を「ヤフオク出品写真」「自社Amazon出品写真」「共通カタログ画像」と明示する。画像は縦横比を保ち、実物の状態が隠れる切り抜きをしない。
- 一覧の代表画像は、まず対応するヤフオク画像を候補とする。自社Amazon出品写真が正しく取得できる場合は詳細で並べて比較できる設計とし、一覧に写真を何枚も並べない。
- 自社Amazonの短いコメントは商品行の2段目に1〜2行で表示し、「全文」で開く。入力されていない場合と取得できない場合を区別する。
- メモは通常は文章。「編集」を押したときだけ入力欄と「保存」「取消」を出す。全行に常設の大きな入力欄と保存ボタンを並べない。
- 一覧上部に「登録商品の情報を更新」を1つ置く案。対象は登録商品のみ。普段は商品ごとの画像取得ボタンを並べず、失敗時の再取得をその商品の詳細へ置く。
- 「解除」は詳細メニュー内へ置き、登録や編集ボタンの近くで誤操作しにくくする。実行前に対象を示す。
- 在庫確認時刻は数量のそばに置く。数量が正でもMCF出荷可否が未確認なら、その旨を短く併記する。詳細で理由を示し、緑の成功表示だけで発送可能と誤解させない。
- 補足にはSKU/FNSKU・数量の内訳・取得時刻・出所・履歴・技術的根拠を置く。
- 商品名/ASIN/出品IDによる一覧内検索を候補とする。初期状態で複雑な絞込パネルを出さない。

スマホは窮屈な3〜4列を維持せず、1商品ごとの縦積みにする。写真と商品名、数量、両リンク、コメント、メモの順で表示する。繰り返し商品枠を入れ子のカードにしない。文字は原則16px、操作領域は44px程度を目安にする。色だけで状態を伝えず、文字ラベルと入力欄に対応するエラー表示を付ける。

### 通知とメール

通常は「要対応○件」と最新の要点を表示し、通知一覧・プレビューは必要時に開く。結論と必要対応は折りたたまない。技術情報と履歴のみ補足にする。

架空の表示例：

> FBA在庫を確認できません。再取得してください。
>
> ［商品写真］モニター E232 スタンドなし
>
> Amazon：B0DEMO0001 ／ ヤフオク：d1000000001
>
> 在庫切れと確定したわけではありません。
>
> ［再取得］　［補足情報］

- 紐付け不明・FBA在庫不足・取得失敗・出品終了を一括して「紐付いていません」にしない。
- 新規紐付けメールは「紐付けが完了しました」を先頭にし、商品名・ASIN・ヤフオク出品リンクを載せる。画像や商品名が未取得でも正しい識別子で案内できるようにする。
- 同じ組の再登録は新規通知を作らない。まとめ登録時は、複数商品を1通へまとめる案を推奨するが、送信単位は本人確認後に確定する。
- 「登録済み」「情報取得中／取得済み／取得失敗」「メール未送信／送信処理中／送信受付済み／失敗／結果不明」を分ける。送信受付済みを受信箱到着確認と呼ばない。
- 通知は保存済みの送信待ち記録から処理する設計。メール失敗で商品登録を戻さず、無条件の再送もしない。送信結果不明は重複リスクを示して別扱いにする。
- 過去に登録した商品へ自動で一斉メールを送らない。在庫通知・定期監視の有効化は別途確認する。

## 4. 取得する情報と同定

ASINは入力の手軽さのために使うが、自社在庫・コメント・写真の内部照合は自社アカウント、マーケットプレイス、Seller SKUで行う。競合出品やカート取得者から自社情報を推測しない。

| 情報 | 取得候補・既存処理 | 未取得や曖昧な場合 |
| --- | --- | --- |
| ヤフオク画像・商品名 | 対応IDを照合した公開ページの構造化商品名と代表画像 | 名前未取得・画像なし。商品登録は保持 |
| 自社FBA数量 | 既存の対象ASIN検索と対象SKU限定の在庫取得 | 不明・古い情報・複数該当を明示。0にしない・合算しない |
| 自社コンディションコメント | 自社Listingsの属性取得を候補として調査 | 実際に未入力と確認できた場合のみ「記載なし」。それ以外は「未取得／確認できず」 |
| 自社出品写真 | 自社SKUの属性で出所・対象を確認できる画像を候補として調査 | カタログ画像を自社写真と呼ばない。取得不能ならその旨を表示 |
| Amazon共通の商品名・画像 | 自社出品情報とは別の参考情報 | 共通カタログと明記。御社の実物状態の証拠にしない |
| 自分用メモ | その紐付けに対するローカル保存 | 自動取得で上書きしない。公開コメントや一致判定の根拠へ自動転用しない |

同一ASINに複数の自社SKUがある場合は例外として要確認にする。選択が必要なら、写真・状態・コメントで選び、通常作業でSKUを打ち込ませない。区別できない場合は保留。数量とMCFへの充当可能性は別の確認事項であり、取得分0もASIN全体の在庫切れとは断定しない。

Amazon公式資料では、自社出品者を指定するListings検索・SKU指定の詳細取得に `attributes` を含められることを確認した。これは取得方法の候補があるという意味で、御社のコメント・中古出品写真が実際に返ることを保証しない。[searchListingsItems](https://developer-docs.amazon/sp-api/reference/searchlistingsitems)、[getListingsItem](https://developer-docs.amazon/sp-api/reference/getlistingsitem)

Amazonはカタログ情報とSKUごとの出品情報を区別しており、商品属性は商品タイプの定義に依存する。実装前に対象商品の応答で必要項目を確認する。本設計作業では御社APIを呼んだり権限を追加したりしていない。[Amazon出品管理ガイド](https://developer-docs.amazon/sp-api/docs/manage-product-listings-guide)

## 5. 保存と更新のルール案

- 既存の紐付けID・リンク・履歴を維持し、必要項目を追加する。過去データのメモなし・画像なしを正常に扱う。
- 自分用メモ、自社コメント、カタログ説明、画像出所、在庫情報、メール送信状態は別の項目へ保存する。既存の `reviewNote` を自分用メモとして上書きしない。
- 画像・コメント・数量はそれぞれ出所と確認時刻を持つ。一括更新の一部失敗で、他の取得済み項目やメモまで消さない。
- 商品情報の更新で、出品者の確認・管理番号の一致・出品終了を勝手に確定しない。表示情報の取得と安全判定を分離する。
- メモ編集中の情報更新は入力内容を維持する。保存失敗でも入力は残す。未保存で再読込・移動するときは確認し、取消は直前の保存内容へ戻す。
- 同時操作の上書き防止も確認する。保存リクエストは対象IDと変更項目に限定し、古い画面全体でサーバーデータを上書きしない。

## 7. 承認後の作業順と合格条件

1. 本人の登録作業が区切れたことを確認し、読み取りで現在の登録と稼働状態を把握する。必要な保存データをバックアップし、既存データをリセットしない。
2. 架空商品の画面見本を別の検証環境で確認する。商品名・写真・数量・自社コメント・メモがすぐ区別できること、長い名前や画像なしでも崩れないことを確認する。
3. 許可後に登録商品の少数例だけで、自社コメント・出品写真の取得可能性を読み取り検証する。全在庫取込なし、他社データ混入なし、未取得を維持。追加権限が必要なら実行前に相談する。
4. 1件登録、まとめ登録の部分成功・重複・競合、メモの保存・取消・再読込・更新中の保護を隔離データで検証する。画像取得失敗で登録が失われないことも確認する。
5. 在庫不明・取得分0・複数SKUを誤って確定扱いしないことを確認する。PC/スマホで文字や操作が重ならず、画像が実際に表示されることをブラウザで確認する。
6. メールはプレビューと模擬送信で、重複抑制・保存後の再起動・失敗と結果不明を検証する。本人了承後の実送信テストと自動通知有効化は別に行う。
7. 本番反映は本人の作業が終わった後に行い、再起動が必要なことを先に知らせる。反映前後で既存の登録が保持されることを確認する。

## 8. 独立UIレビューと採否

レビュー担当タスク：「ASIN・ヤフオク通知画面のUIレビュー」／`01a15a2c-2576-7191-800f-99eb9181fa19`。本人の今回の依頼に基づく第2回レビュー。既存の別タスクを再利用し、モデル・サブエージェント設定は変更していない。ソースと架空商品のテスト画像のみを確認し、稼働ブラウザ・実データ・サーバーを操作しない条件で依頼。回答でも未操作と報告された。

- 採用案：登録欄＋一覧＋要対応通知、通常2欄、まとめ登録の行別結果、常設ボタンを減らす、メモは編集時のみ入力、写真の出所、数量とMCFの区別、スマホ縦積み。
- 現行コードの見直し点：全行のメモ入力・保存・画像取得ボタンと、狭いスマホ3列は完成形としない。
- 保留：Amazon自社コメント・出品写真の実取得、まとめ登録メールの送信単位、情報更新の対象項目・頻度。取得不能なら手動入力を必須にせず、未取得を許容する。
